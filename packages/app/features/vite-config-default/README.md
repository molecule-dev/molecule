# @molecule/app-vite-config-default

`@molecule/app-vite-config-default` — drop-in Vite config factory.

`createDefaultViteConfig({ APP_NAME, APP_DESCRIPTION, BRAND_COLOR })`
returns the canonical fleet vite config (react + tailwind + VitePWA,
molecule-package pre-bundle exclusion, /api + /health + /socket.io (ws)
proxy, push service worker). Per-app `vite.config.ts` shrinks from 105
lines to 5. Also exports `moleculePushServiceWorkerPlugin` /
`PUSH_SW_FILENAME` / `PUSH_SW_SOURCE` (the web-push half of the
generated service worker).

Any other UI framework uses the same config through
`createFrameworkViteConfig(branding, { plugins })` from
`@molecule/app-vite-config-default/framework`: pass the framework's plugin and,
when the styling needs one, its build plugin (`[vue(), tailwindcss()]`). That entry
loads neither `@vitejs/plugin-react` nor `@tailwindcss/vite` (the package root does,
for `createDefaultViteConfig`). A SvelteKit app also passes `svelteKit` (its page and
site hooks), and `warmup` names the files the dev server transforms first.

## Quick Start

```ts
import { defineConfig } from 'vite'

import { createDefaultViteConfig } from '@molecule/app-vite-config-default'

// In a scaffolded app these come from './src/branding.js'.
const APP_NAME = 'Acme'
const APP_DESCRIPTION = 'Acme dashboard'
const BRAND_COLOR = '#6750a4'

// The app's vite.config.ts wraps this exact call in `export default`.
const config = defineConfig(createDefaultViteConfig({ APP_NAME, APP_DESCRIPTION, BRAND_COLOR }))
```

#### `createFrameworkViteConfig(branding, options)`

The Vite config every Molecule app uses, for any UI framework: the framework's
plugins plus the PWA, push worker, release notes and root-relative asset plugins,
molecule-package pre-bundle exclusion, one module identity per package, the dev
server and `vite preview` proxy for `/api`, `/health` and `/socket.io` (ws), and the
standard env conventions. A SvelteKit app passes `svelteKit`, and the PWA steps run on
the site kit's adapter writes.

```ts
  createFrameworkViteConfig({ APP_NAME, APP_DESCRIPTION, BRAND_COLOR }, { plugins: [vue()] }),
)
```

#### `svelteKitStaticSite(options)`

The plugin that finishes a SvelteKit app's site after kit's adapter has written it:
rewrites every page ({@link SvelteKitStaticSiteOptions.transformPage}), adds the
`<link rel="manifest">` vite-plugin-pwa adds to a Vite `index.html`, runs
{@link SvelteKitStaticSiteOptions.finishSite}, then generates the service worker from the
files really there. It refuses a build whose site has no `index.html` (the adapter wrote
somewhere else), since the deploy would have no page. It also makes `vite preview` answer
from the site, as the deployed front does, rather than from kit's server build.

Use it with `@sveltejs/adapter-static`'s fallback page (`adapter({ pages: 'dist', assets:
'dist', fallback: 'index.html' })`), {@link svelteKitPwaPlugins} and
{@link svelteKitPrecache}. `enforce: 'post'` with a `post` `buildApp` hook puts it after
kit's adapter wherever it sits in `plugins`.

```typescript
function svelteKitStaticSite(options?: SvelteKitStaticSiteOptions): Plugin
```

- `options` — The site directory and the app's own page and site steps.

**Returns:** The Vite plugin.

```typescript

{ title: text } : null\n    }\n    if (!payload || !payload.title) return null\n\n    var options = Object.assign({}, payload.options || {})\n    if (options.body === undefined && typeof payload.body === 'string') {\n      options.body = payload.body\n    }\n    var extra = Object.assign({}, options.data || {})\n    if (extra.href === undefined && typeof payload.href === 'string') {\n      extra.href = payload.href\n    }\n    options.data = extra\n    return { title: payload.title, options: options }\n  }\n\n  self.addEventListener('push', function (event) {\n    var notification = normalizePushPayload(event.data)\n    if (!notification) return\n    event.waitUntil(\n      self.registration.showNotification(notification.title, notification.options),\n    )\n  })\n\n  self.addEventListener('notificationclick', function (event) {\n    event.notification.close()\n    var data = event.notification.data || {}\n    var href = typeof data.href === 'string' && data.href ? data.href : '/'\n    event.waitUntil(\n      self.clients\n        .matchAll({ type: 'window', includeUncontrolled: true })\n        .then(function (clients) {\n          var client = clients && clients.length > 0 ? clients[0] : null\n          if (!client) {\n            return self.clients.openWindow(href)\n          }\n          var focused = client.focus()\n          // Best-effort deep link; not every focused client can navigate\n          // (cross-origin/uncontrolled), and focusing alone is still correct.\n          if (href !== '/' && typeof client.navigate === 'function') {\n            return Promise.resolve(focused)\n              .then(function () {\n                return client.navigate(href)\n              })\n              .catch(function (_error) {\n                return client\n              })\n          }\n          return focused\n        }),\n    )\n  })\n})(self)\n"
```

### Runtime Dependencies

- `@jridgewell/trace-mapping`
- `@molecule/app-version`
- `@tailwindcss/vite`
- `@vitejs/plugin-react`
- `vite`
- `vite-plugin-pwa`

Production builds with VitePWA and `@molecule/app-pwa-default` bundle that
package's guarded registrar into the HTML entry. Existing startup calls to
the package are safe alongside it. The navigation fallback leaves the API,
health and realtime routes on the network.

**`vite preview` proxies the API too.** `npm run build && npx vite preview` serves the
production bundle (`dist/`, port 4173) with the same `/api`, `/health` and `/socket.io`
routes as the dev server, so the e2e suite can run against the bundle that ships — a bug
that exists only in the production build shows there before a deploy.

**Dev-server host exposure is environment-detected: molecule sandbox vs
standalone machine.** Inside a molecule preview container (`/etc/mol`
exists, or `VITE_HOST` is set) the dev server binds `0.0.0.0` with
`allowedHosts: true` and `fs.strict: false` — the IDE preview iframe on
the host must reach it by IP/internal hostname, and modules resolve
through workspace symlinks outside the project root. Everywhere else
(a developer's machine running `npm run dev`) those settings are the
LAN-exposure + DNS-rebinding + `/@fs/` file-read triad, so standalone
defaults are `host: 'localhost'`, Vite's Host allowlist (localhost
variants, extended via `VITE_ALLOWED_HOSTS=myapp.test,dev.lan`;
`VITE_ALLOWED_HOSTS=*` disables Host checking entirely), and Vite's
strict `fs` confinement. `VITE_HOST` overrides the bind address in both
modes.

Env conventions the config reads: `VITE_PORT` (dev port, default 3000),
`VITE_HOST` (explicit bind address — also selects sandbox behavior),
`VITE_ALLOWED_HOSTS` (standalone Host-allowlist extension),
`VITE_API_URL` (proxy target for /api,
/health, /socket.io; defaults to http://localhost:PORT with PORT
defaulting to 4000), `VITE_CACHE_DIR` (per-app Vite cache dir — under
workspace-symlinked node_modules the default cache is shared machine-wide
and corrupts under concurrent dev servers), and `VITE_OPEN=false` or
`BROWSER=none` to stop the dev server auto-opening a browser tab (vite's
`--open` flag takes no value — from automation, use the env vars).

Every `@molecule/*` package is EXCLUDED from dependency pre-bundling
(bond state lives in module-level singletons; pre-bundling duplicates
them and silently breaks `bond()` wiring) — EXCEPT
`@molecule/app-locales-*` bonds, which are force-included because they
are pure data and unbundled they fan out into thousands of dev-server
module requests. `resolve.dedupe` lists every installed `@molecule/*`
package (one module identity per package, whichever install path an
importer reaches it through — two identities would mean two bond
registries and two query caches) plus `react`, `react-dom`,
`react-router` and `react-router-dom`; when a `@molecule/*-react`
package calls hooks from another peer library (zustand,
`@tanstack/react-query`, ...), that library must be added to dedupe too or
two module instances break its React context. A CJS dep that crashes
with "does not provide an export named 'default'" should be declared as
`"molecule": { "viteOptimizeInclude": ["<dep>"] }` in the package.json
of the `@molecule` package that OWNS the dep — this factory aggregates all
such declarations into `optimizeDeps.include` automatically.

The factory takes no options beyond branding — extend the result with
vite's `mergeConfig(createDefaultViteConfig(branding), overrides)`.
The PWA build emits `push-sw.js` and importScripts it into the Workbox
generateSW worker so delivered web-push notifications actually display.
It also writes `release-notes.json` and stamps the build's commit time into
`index.html` (`releaseNotesPlugin` from `@molecule/app-version/build`), which the
update banner reads to say in one line what a waiting update brings. The
notes come from the app directory's conventional commits (`feat:`, `fix:`,
`perf:`), so a build outside a git checkout simply ships no summary.

**Root-relative images must ship.** A production build fails with the original
source file and line when an app module names `/image.svg` (or png, jpg, jpeg,
gif, webp, avif, ico) but the output lacks that file. Put the file in `public/`
or import it from `src/`. Files emitted by other plugins count too. Proxied
routes, external URLs, comments and interpolated templates are excluded.
`rootRelativeAssetsPlugin()` exports the same build check for custom configs.
It also reports source files outside the production graph with their paths
and where to import or reference them. Test sources, declarations, configs
and public files are exempt. Prerender builds use the same plugin instance
for their client and server passes so files used by either pass count.

**A custom config imports the plugins it needs from their own entries.** The package root
and `/framework` load `vite-plugin-pwa`; `@molecule/app-vite-config-default/assets`
(`rootRelativeAssetsPlugin`) and `@molecule/app-vite-config-default/dist-sourcemap`
(`moleculeDistWithoutSourcemap`, which serves each `@molecule` package's JavaScript without
the sourcemaps that name source files the package does not ship) load only Vite and Node.

**A SvelteKit app deploys the same site.** `@molecule/app-vite-config-default/sveltekit`
finishes the static site `@sveltejs/adapter-static` writes to `dist/` (with
`fallback: 'index.html'`): `svelteKitStaticSite()` adds the web-manifest link, runs the
app's page and site steps, generates the service worker after the adapter, refuses a
site with no `index.html`, and makes `vite preview` answer from the site as the deployed
front does. `svelteKitPwaPlugins(VitePWA(options))` takes out the hooks SvelteKit never
calls, and `svelteKitPrecache()` precaches kit's shell files.

The config also carries vitest's `test.exclude`, keeping the Playwright
suite under `e2e/` out of `npm test` (`vitest run`): Playwright specs are
`*.spec.ts`, which vitest's default include would otherwise collect and
fail. Put unit tests under `src/` and Playwright specs under `e2e/`
(`playwright.config.ts` → `testDir: './e2e'`); if you override
`test.exclude`, keep the `**\/e2e/**` entry.
