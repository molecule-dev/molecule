# @molecule/api-ai-tools

Shared AI agent tool set for molecule.dev — filesystem, search, and shell
tools an LLM agent can call, with a swappable execution backend.

`buildTools(backend)` returns ready-to-use `AITool`s (the `@molecule/api-ai`
tool shape): `list_files`, `read_file`, `write_file`, `edit_file`,
`search_files`, `find_files`, `create_directory`, `rename_file`,
`delete_file`, `exec_command`, `save_plan`, `load_skill`. The backend decides
WHERE they act: `createLocalBackend(projectRoot)` (host filesystem) or
`createSandboxBackend(...)` (an isolated `@molecule/api-code-sandbox`
container). `buildAgentPrompt(ctx)` composes a matching system prompt
(identity, tool listing, project docs, discovered skills).

## Quick Start

```typescript
import { buildAgentPrompt, buildTools, createLocalBackend } from '@molecule/api-ai-tools'
import { requireProvider } from '@molecule/api-ai'

const backend = createLocalBackend('/path/to/project')
const tools = buildTools(backend, { include: ['read_file', 'edit_file', 'search_files'] })
const system = buildAgentPrompt({
  agentName: 'My Agent',
  projectRoot: backend.projectRoot,
  tools: tools.map((t) => t.name),
})

// Hand them to the bonded AI provider (or an @molecule/api-ai-agents run).
for await (const event of requireProvider().chat({ system, tools, messages, stream: true })) {
  // forward text chunks; tool calls are executed against the backend
}
```

#### `LocatedCommandSegment`

One statement of a shell command, with where it sits and the variables it sets for itself.

`commandSegments` answers WHAT runs; this answers where, and what the shell binds to it — the
two things a caller that WRITES into a command needs. The platform composes a run from the
executor's own command in more than one place, and a value written for the runner belongs in
the runner's own statement: `APP_BASE=https://… cd app && npx playwright test` sets the variable
for `cd` alone, so the Playwright config falls back to the local app while the command line
still names the deployed host (xr-molecule-flash-m103 +28:08).

```typescript
interface LocatedCommandSegment {
  /**
   * What the statement runs, or null when it only sets variables (`BASE=http://…` on its own):
   * that shape persists in the shell, so a caller following assignments across `;`/`&&` has to
   * see it.
   */
  segment: CommandSegment | null
  /** The statement's own leading `NAME=value` words, as written (`TEST_MODE=fullstack`). */
  assignments: readonly string[]
  /**
   * The offset in the command of the statement's first word, or null for a segment inside a
   * nested `sh -c '<command>'` string — its positions are offsets in THAT string, not in this
   * command, so nothing may be spliced at them.
   */
  start: number | null
  /**
   * The offset in the command just before the word the statement runs — after its own leading
   * `NAME=value` words and their whitespace. A `NAME=value` written here is in the environment of
   * the program the statement runs (`… TEST_MODE=fullstack <here>npx playwright test`). Null
   * inside a nested `sh -c` string, for the same reason as {@link start}.
   */
  assignmentOffset: number | null
  /**
   * The offset in the command one past the statement's last word — where an option of this
   * statement's program belongs, before whatever closes it. Null inside a nested `sh -c` string.
   */
  end: number | null
  /**
   * The offset in the command of the word in command position — the program, once every wrapper
   * in front of it is taken away (`npx --prefix /app <here>playwright test`). Null inside a
   * nested `sh -c` string, and for a statement that only sets variables.
   */
  programOffset: number | null
  /**
   * The separator the shell split at immediately before this statement — `|`, `||`, `&&`, `;`,
   * a newline or `&` — or '' when it is the first statement of the command. It is the parse's own
   * answer, so it is known even where the offsets are not, and a caller deciding whether two
   * statements are one pipeline (`|`, never `;`) asks it instead of reading the text between them.
   */
  separator: string
  /**
   * The separator that ENDED this statement — `&` when the shell backgrounds it (so the process
   * writes its own output, not the command's), '' for the last statement of a command.
   */
  terminator: string
  /**
   * The file this statement sends its own output to (`> out.log`, `>> log`, `&> run.log`,
   * `| tee file`), or null. Only a redirect written at the command's own level counts: one
   * inside a `( … )` / `{ … }` group writes through that group, and one that feeds a heredoc's
   * file (`cat > cfg.ts <<'EOF'`) is writing a config (X1 flash-m44, flash-m136).
   */
  redirectTarget: string | null
}
```

#### `SuiteSummary`

What a runner's own closing summary reports, and whether it accounts for the whole run.

A summary is not by itself proof that the run finished. Playwright prints one when its process
is stopped too (SIGTERM/SIGINT), listing only the tests it reached — so a run killed at 36 of
139 tests ends with the same `36 passed (2.5m)` line as a run that walked all 139. The only
thing that separates them is the total the runner announced before it started
(`Running 139 tests using 1 worker`), which {@link suiteSummary} reconciles the summary against.

```typescript
interface SuiteSummary {
  /**
   * The total the runner announced before its first test, or null when it announced none (Hurl
   * announces nothing; Vitest's own summary line carries its total in parentheses).
   */
  announced: number | null
  /**
   * Every test the summary accounts for — the ones it passed, failed, marked flaky, timed out,
   * interrupted, skipped or left "did not run". This is how far the walk got, which is what a
   * stopped run's sentence says; a summary that accounts for fewer than {@link announced} was
   * printed by a process that stopped early.
   */
  accounted: number
  /** Whether the summary accounts for every test the runner announced. */
  finished: boolean
}
```

Implemented by SandboxBackend (Docker) and LocalBackend (host filesystem).

```typescript
interface ExecutionBackend {
  /** The root directory for all operations (e.g. '/workspace' or '/Users/.../project'). */
  readonly projectRoot: string

  /**
   * Marks backends that operate DIRECTLY on the host filesystem (the local
   * backend), as opposed to a contained sandbox. Consumers use it to judge
   * how loud to be about disabled safety guards — a `..` path or symlink
   * escape on a host backend reaches the operator's real files, while the
   * same escape in a sandbox stays contained.
   */
  readonly hostFs?: boolean

  /** Read a file's content as UTF-8 string. */
  readFile(path: string): Promise<string>

  /** Write content to a file. Creates parent directories as needed. */
  writeFile(path: string, content: string): Promise<void>

  /** Delete a file. */
  deleteFile(path: string): Promise<void>

  /** List entries in a directory. */
  readDir(path: string): Promise<Array<{ name: string; type: 'file' | 'directory' }>>

  /**
   * Run a shell command. Returns stdout, stderr, and exit code.
   * Backends implement this safely (sandbox.exec for Docker, execFile for local).
   */
  run(
    command: string,
    opts?: {
      cwd?: string
      timeout?: number
      /**
       * A budget (ms) the backend enforces INSIDE its own shell, after any
       * environment sourcing a consumer wraps around the command — so an
       * overrun is stopped where it runs and the output so far still comes
       * back, with exit code 124. A backend that cannot enforce it ignores it.
       */
      budgetMs?: number
    },
  ): Promise<{ stdout: string; stderr: string; exitCode: number }>
}
```

```typescript
   * that wraps tool calls in its own outer timeout should set this to match (or
   * slightly exceed) that budget so its own timeout is the effective bound and
   * produces the nicer "tool timed out" message. Quick commands are unaffected —
   * this is only the ceiling before a wedged command is killed.
   */

   * so when it overruns it is stopped there and the tool still returns

   * discards minutes of build or test output along with the result. Set it a
   * little under that outer timeout. Unset = no budget.
   */
  commandBudgetMs?: number

  searchExcludedDirs?: string[]

  outlineLargeHtml?: () => boolean
```

#### `statementArgumentEnd(command, start, end)`

redirection (`… 2>&1`), and a statement can sit inside a group whose closer belongs to the
shell, not to the words (`( … )`, `{ …; }`). Appending after that closer is a different shell
word that the group has already closed — `… --config=x 2>&1) --reporter=list` is
`sh: Syntax error: word unexpected`, which killed a backgrounded walk at once and pushed the
model off the platform's runner shape (xr-molecule-flash-m129 +34:29). Write the option where
the program's own arguments end and the rest of the statement still parses:
`… --config=x --reporter=list 2>&1)`.

inside a nested `sh -c '<command>'` string has no offsets here (its positions are positions in
that string), so null is returned rather than a splice into the outer text.

```typescript
  start: number | null,
  end: number | null,
```

#### `withoutTimeoutWrapper(command, which)`

The command with the `timeout <N>` wrapper lifted off the statements `which` selects, and the
largest bound that was lifted.

The platform moves a run to the background precisely because its own bound cannot fit this
tool's ceiling, and a background task has no ceiling — its wait is bounded by `wait_for_task`
and the turn's deadline. The `timeout N` an executor wrote to fit the ceiling therefore keeps
killing the run at N in the background, where nothing needed it: X1 xr-molecule-flash-m143
(+24:45) wrote `timeout 280` for a 31-test walk, the tool backgrounded it, and the prefix stopped
the walk with no tally — then the cut sentence told the executor to "run it in the background",
which is where it already was.

The wrapper is found by the same parse every other command reader uses ({@link commandStart}):
`timeout` in an argument bounds nothing, and the wrapper's own flags (`-k`/`--kill-after`,
`-s`/`--signal`) are stepped over, so `timeout -k 5 280 …` is `280`.

```typescript

  command: string,
  which: (segment: CommandSegment) => boolean,
): { command: string; seconds: number | null }
```

- `command` — The shell command.
- `which` — The statements to lift the wrapper from (a suite run, for the background path).

**Returns:** The rewritten command, and the largest lifted bound (null when nothing was lifted).

#### `commandCutRun(command, result, elapsedMs, budgetSeconds, rawOutput)`

The run a command's result records as stopped by a budget, or null when the result is a run that
ended (or says nothing about a run).

Evidence, in order — never a guess:

- the runner's own summary, when it printed one: it is a finish only if it accounts for the total
  the runner announced. A summary that accounts for fewer is a walk a process stopped early, and
  falls through to the branches below with its own counts ({@link suiteSummary}).
- `timeout`'s own 124 (the code the backend's wrapper returns whenever the TOOL's budget fired,
  whatever the pipeline ended with) — and, when the clock says the command's own smaller bound
  ran out first and less than the budget, that bound instead.
- the command carried its own `timeout <N>`, N is inside this tool's budget (a larger one never
  fires — the tool's does), the run used N, and no runner printed a closing summary: the run was
  killed at its own bound. Its exit code, when the pipeline handed one back, is the filter's.
- the run used this tool's whole budget behind a filter that withheld its output, and printed no
  closing summary: the budget stopped it, and no code in the result is the run's.
- a summary that does not account for its announced total, with neither bound fired: something
  outside this platform stopped the process ({@link CutBy} `process-stop`).

```typescript
function commandCutRun(
  command: string,
  result: unknown,
  elapsedMs: number,
  budgetSeconds?: number,
  rawOutput?: string,
): CutRun | null
```

- `command` — The command the executor sent.
- `result` — Its result.
- `elapsedMs` — How long the command ran, in ms.
- `budgetSeconds` — This tool's foreground budget, in seconds (0 when it has none).
- `rawOutput` — The run's output BEFORE truncation, when the caller has it: the announcement a summary is reconciled against is the first line a long run prints, which is exactly what a size cap drops. Detection reads this; the sentence's last line still comes from `result`.

**Returns:** The stopped run, or null.

#### `cutRunSentence(run)`

The first line of a stopped run's result: how far it got, what stopped it, the last thing it
printed, and what the reader must do next.

Written to be quotable by the model in one sentence and to leave no room for "nearly passing":
the counts come from the runner's own output ({@link runProgress}), and a `total` the caller

#### `MAX_READ_CALL_CHARS`

The most one `read_file` RESULT may carry, in chars of its JSON — every file
the call returns, the envelope and the note included. That is how the request
side counts a tool result, so it is how this tool counts one too
({@link serializedChars}).

One tool result is ONE block in the request, and the request side caps a
block: molecule-dev cuts any block over `MAX_TAIL_BLOCK_CHARS` (60,000) in
place, keeping ~30 KB of each end. A batched read that crossed it lost its
MIDDLE — the cut lands between two `"content"` values, so whole files fell
out and the note in their place said only "N characters cut here" — while
this tool's own note had promised each of those files that it "fits in one
call, so it is not paged": X0 flash-m81 (2026-10-16) read ten e2e specs in
one call (121,467 chars), lost the middle six, and bought them again in six
further calls (52,908 chars).

So the CALL gets the ceiling the request gives it. Whole files are returned
up to it; the paths that did not fit are named in `note` and listed in
`files` with their own `error`, the shape every other entry has. No file is
ever cut, and no read result reaches the request-side cut. A test in
molecule-dev's `context-fit` asserts the two ceilings still agree.

```typescript
const MAX_READ_CALL_CHARS: 60000
```

## Injection Notes

### Requirements

Peer dependencies:

- `@molecule/api-ai` ^1.0.1

### Runtime Dependencies

- `@molecule/api-ai`

- **This package only defines the tools — it runs no model loop.** Hand them to
  the bonded AI provider (`chat({ tools, … })`) or to an
  `@molecule/api-ai-agents` run.
- **Safety defaults: keep them on for model-driven use.** `pathGuards` (default
  true) rejects paths escaping `projectRoot`; `redactSecrets` (default true)
  masks secret-looking values in file reads and command output.
- **`exec_command` executes REAL shell commands** on the backend. Prefer a
  sandbox backend for untrusted/model-driven work; add environment-specific
  rules via `blockCommand` (return an actionable error string to refuse — it is
  shown to the model verbatim) and enable `blockDangerousCommands` (default
  FALSE) where appropriate.
- **`read_file` takes `paths` as well as `path`.** An agent that issues one
  tool call per model round-trip pays a full round-trip per file, so a project
  survey costs minutes; batched, the same reads cost one call each 25 files
  (`MAX_BATCH_READ_FILES`). One result is capped at `MAX_READ_CALL_CHARS`, the
  ceiling the request side puts on a single tool result: whole files are
  returned up to it and every path past that is named in `note` and listed as
  `not returned`, so a file is never handed back in part — the shape that lost
  the middle of a ten-file batch to the request-side cut (X0 flash-m81). Each
  entry carries its own content or its own error, so one bad path never fails
  the batch.
- **`edit_file` shows the result, so the model need not re-read.** A
  successful edit returns `excerpt`: each edited region as it now reads, with
  1-based line numbers (`N: text`) and a few lines of context, capped at
  60 lines in total (what did not fit is named by line range),
  plus `totalLines`. `write_file` returns `totalLines`, and `excerpt` only
  for a small file (up to 40 lines) — a big file is never echoed back.
  Line numbers count the way `read_file` does, so they are valid offsets. The
  excerpt is redacted like a read. The existing fields (`ok`,
  `replacementsApplied`, `alreadyApplied`, `syntaxError`) are unchanged.
- **A dropped line break and the parse error it causes are reported as ONE
  thing.** When a replacement's `old_string` ended with a newline and its
  `new_string` does not (so the next line is pulled up onto it) and the file
  then fails its parse check, `edit_file` returns a single `syntaxError` that
  names the replacement, shows the fused line with its number, and says to
  re-send that replacement with the newline restored — instead of the
  `newlineNote` hint beside an unrelated-looking parse error, which an executor
  repairs by rewriting the fused line's text and fuses the next one. The
  `newlineNote` alone is still returned when the file parses.
- **A replacement that only changes a line break at its boundary is refused,
  not applied.** When `new_string` is `old_string` with its trailing newline
  added or removed and nothing else, the edit can only move text across lines —
  joining the next line onto the replaced text, or pushing the rest of the line
  down — which is what a weak model does by accident when it repeats a line it
  means to keep (flash-m28, m55, m62, m89, five times in the m89 run alone). The
  replacement is skipped, the rest of the batch is applied, and the result
  carries `skippedNote`: one line naming the replacement, what applying it would
  have done, and how to say it on purpose (include the next line in `old_string`).
  The file's own next character decides: text on the same line is a join or a
  split and is refused; a blank line after it, or the end of the file, means no
  text crosses lines and the edit is applied as written.
- **A parameter under another name is not a broken tool.** Every tool's input
  is normalized first (`cmd` → `command`, `file` → `path`, camelCase ⇄
  snake_case), and a handler that throws returns an error naming the missing
  parameter rather than a bare internal message — which a weak executor reads
  as a broken tool and routes around, taking its verification with it. Use
  `guardAITool` to give tools built elsewhere the same treatment, passing
  `redactError` so a thrown message is masked by your own redactor.
- **Scope the tool set per agent** with `include`/`exclude` — a read-only agent
  should not receive `write_file`/`exec_command`.
- Outputs are size-capped (`MAX_READ_SIZE`, `MAX_OUTPUT_SIZE`, …) and searches
  skip `DEFAULT_SEARCH_EXCLUDED_DIRS` (node_modules, VCS dirs, build output) —
  pass `searchExcludedDirs` so every search surface shares the consumer's one
  setting.

## E2E Tests

Integration checklist — drive the real UI (live preview, no mocks), adapt
each item to this app's actual agent/chat surface and its registered tools,
and check every box off one by one. A box you can't check is an integration
bug to fix — not a skip:

- [ ] A prompt that should trigger a registered tool makes the model INVOKE
      it with args matching that tool's `parameters` schema (e.g. "read
      src/index.ts" -> calls `read_file` with `{ path: 'src/index.ts' }`).
      Confirm the tool's `execute` actually RAN — its backend side effect / log /
      the file it touched — not that the model merely narrated calling it.
- [ ] The tool's returned value flows back into the model and shapes the
      final answer: the REAL result (the file's actual contents, the command's
      real stdout/exitCode) appears in the reply, not a plausible hallucination.
- [ ] A prompt that needs no tool is answered directly, with no spurious
      tool call.
- [ ] A tool whose `execute` throws or returns `{ error }` (missing file,
      failing command, blocked path) degrades gracefully — the error is caught
      and fed back to the model as text, the conversation continues, and nothing
      crashes the request.
- [ ] The model can invoke ONLY the tools handed to this run: an
      `include`/`exclude`-scoped agent (e.g. read-only — no `write_file` /
      `exec_command`) cannot call an excluded tool, and a tool name the model
      invents that was never registered is refused, not executed.
- [ ] Tool execution is server-side and authorized: `exec_command` /
      `write_file` run only on the bonded backend under its guards (`pathGuards`,
      `symlinkGuards`, `redactSecrets`, `blockDangerousCommands` / `blockCommand`)
      and stay inside `projectRoot`. Feed a prompt-injected instruction (a file or
      message telling the model to read `/etc/passwd`, escape the workspace, or run
      a privileged command) and confirm the guard REFUSES it — a user must not be
      able to trigger, via the model, any action they could not perform directly.
