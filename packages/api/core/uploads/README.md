# @molecule/api-uploads

Uploads core interface for molecule.dev.

Defines the standard interface for upload providers, {@link receiveUploads}: the route
middleware that receives a request's files into the bonded provider, and {@link sendUpload}, which
serves a stored file back as a download the browser does not open (never `stream.pipe(res)`).

## Quick Start

```ts
import { getProvider, getUploads, receiveUploads, sendUpload } from '@molecule/api-uploads'
// a bond called setProvider() at startup; the default, `@molecule/api-uploads-filesystem`, stores
// files under FILE_UPLOAD_PATH (./uploads), a folder that ignores itself in git: no .gitignore entry

router.post(
  '/files',
  requireAuth, // refuse anonymous requests before anything is stored
  receiveUploads({
    field: 'file',
    maxFileBytes: 5 * 1024 * 1024, // optional; 10 MiB when left out
    types: ['image/png', 'image/jpeg', 'application/pdf', 'text/plain'],
  }), // refuses: 415 not multipart or another type, 413 too large or too many, 400 no file or another field
  async (req, res) => {
    const [file] = getUploads(req, 'file') // fully stored; refusals never reach here
    await saveFileRow({ id: file.id, userId: getUserId(res), name: file.filename }) // own it
    res.status(201).json({ id: file.id }) // a throw or a 4xx/5xx answer removes the stored file
  },
)

router.get('/files/:id', async (req, res) => {
  const row = await getFileRow(req.params.id)
  if (!row || row.userId !== getUserId(res)) return res.status(404).end() // ownership → no IDOR
  const stream = await getProvider().getFile?.(row.id) // null for any id no stored file has, `../x` too
  if (!stream) return res.status(404).end()
  await sendUpload(res, stream, { filename: row.name }) // a download; { inline: true, type } shows an image
})
```

## API

### Interfaces

#### `ReceiveUploadsOptions`

What an upload route accepts. Anything outside it is refused before the handler runs, with a
translated `{ error, errorKey }` body. The multipart parsing comes from the body parser bond
(`@molecule/api-middleware-body-parser-express` on Express), which `mlcl add` installs and
wires with the upload provider: a route needs only this package.

```typescript
interface ReceiveUploadsOptions {
  /** The form field the files are sent in. A file in any other field is refused with 400. */
  field: string
  /** The largest file accepted, in bytes (default 10 MiB). A larger one is refused with 413. */
  maxFileBytes?: number
  /** The most files accepted in `field` (default 1). More are refused with 413. */
  maxFiles?: number
  /**
   * The MIME types accepted, as the client declares them (`'image/png'`, or `'image/*'` for a
   * whole family). Another type is refused with 415. Omit it to accept any type but those a
   * browser runs (see `allowActiveTypes`).
   */
  types?: readonly string[]
  /**
   * Store files of the types a browser runs when it opens them (HTML, SVG, JavaScript and every
   * XML type). Without it they are refused with 415 `uploads.error.fileTypeBlocked`, on every
   * provider, whatever `types` says. Set it only on a route whose files are served back through
   * `sendUpload()`, as downloads the browser does not open. Never set it on a route that shows its
   * files to users (an avatar, a gallery image): there the file would run on the app's origin.
   */
  allowActiveTypes?: boolean
  /** When false, a request with no file passes with none; by default it is refused with 400. */
  required?: boolean
  /** The most text fields accepted (default 20); they become `req.body`, as strings. */
  maxFields?: number
  /** The largest text field, in bytes (default 64 KiB). A larger one is refused with 413. */
  maxFieldBytes?: number
}
```

#### `UploadRefusedError`

What a provider passes to `upload()`'s `onError` to refuse a file, rather than to report that
storing it failed. `receiveUploads()` answers it as the client's error, with `status` and
`{ error, errorKey }` as JSON, the way it answers a file that is too large; any other error is
the server's, a 500.

```typescript
class UploadRefusedError extends Error {
  /** The HTTP status the refusal is answered with (4xx). */
  readonly status: number
  /** The translation key of the message. */
  readonly errorKey: string
  /** The values the message interpolates. */
  readonly values?: Record<string, string | number>

  /**
   * A refusal, its message translated now.
   *
   * @param errorKey - The translation key of the message.
   * @param values - The values it interpolates.
   * @param defaultValue - The English message, `{{name}}` for each value.
   * @param status - The HTTP status (default 415, a type the server will not store).
   */
  constructor(
    errorKey: string,
    values: Record<string, string | number> | undefined,
    defaultValue: string,
    status = 415,
  ) {
    super(t(errorKey, values, { defaultValue }))
    this.name = 'UploadRefusedError'
    this.status = status
    this.errorKey = errorKey
    this.values = values
  }
}
```

#### `receiveUploads(options)`

Middleware that receives a route's uploaded files into the bonded upload provider.

It refuses, before the handler runs and with a translated `{ error, errorKey }` body: a body
that is not `multipart/form-data` (415), a file over `maxFileBytes` or more than `maxFiles`
files (413), a type outside `types` or one a browser runs (415; see `allowActiveTypes`), a file
in another field or no file (400). When it
refuses, when storage fails, or when the client disconnects, every file it stored for the
request is removed. The handler runs once every file is fully stored: read them with
{@link getUploads}, and the text fields from `req.body` (as strings).

It keeps owning the files after the handler starts. When the route then answers with a status
of 400 or more, they are removed too; a 2xx or 3xx answer keeps them, and so does a client that
goes away before the answer (the handler may already have saved what points at the file). A handler that fails need not clean up itself, though it can with
{@link discardUploads} (before it answers, or when it answers 2xx with the failure in the body).

Put it after the route's authentication check, so an anonymous request is refused before
anything is stored. Calling it only records the options: the parser is built on the first
request, so a router module can be imported (by a test, before the bonds are wired) without a
body parser bond. It throws, when the router loads, for `types` that name a type a browser
runs without `allowActiveTypes: true`. Serve the files back with `sendUpload()`.

```typescript
function receiveUploads(options: ReceiveUploadsOptions): Middleware
```

- `options` — The form field, and optionally the size cap (default 10 MiB), the accepted types and counts.

**Returns:** The route's middleware.

#### `getUploads(req, field)`

The files {@link receiveUploads} stored for this request: the ones still in storage, so none
after {@link discardUploads} removed them.

```typescript
function getUploads(req: unknown, field?: string): UploadedFile[]
```

- `req` — The request.
- `field` — The form field, or every field when omitted.

**Returns:** The stored files, in arrival order; empty when none were sent.

#### `discardUploads(req)`

Removes the files {@link receiveUploads} stored for this request. Call it when the handler fails
after the upload and will not answer with an error status: a handler that reports the failure in
a 2xx body. One that throws, or answers 400 or more, needs no call: the parser removes the files
itself when it sees that answer.

Each file removed is forgotten, so `getUploads(req)` no longer lists it and nothing removes it
twice. A file that cannot be removed is logged and stays listed, for the parser to try again.

```typescript
function discardUploads(req: unknown): Promise<void>
```

- `req` — The request.

- `type` — The stored type.

**Returns:** True for {@link INLINE_UPLOAD_TYPES} and `audio/*` or `video/*` types.

#### `sendUpload(res, stream, options)`

Sends a stored file (the stream `getProvider().getFile(id)` resolves) as the response. By default
it is a download the browser never opens: `application/octet-stream`, `Content-Disposition:
attachment`, `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`, so an
HTML or SVG file, or one whose declared type lied, cannot run on the app's origin. A route that
pipes the stream itself (`stream.pipe(res)`) sends no type, and the browser guesses one.

It never fails on a file's name, whatever the client once sent: a name of any length or encoding
is sent in the header cut to 200 characters.

Pass `{ inline: true, type: file.mimetype }` to show an image, audio, video or plain text file in
the page instead.

```typescript
function sendUpload(
  res: UploadResponse,
  stream: NodeJS.ReadableStream,
  options?: SendUploadOptions,
): Promise<void>
```

- `res` — The response.
- `stream` — The stored file.
- `options` — The file's name, and whether to show it inline.

**Returns:** Resolves when the file is sent; rejects when reading it fails, after closing the response.

### Constants

#### `BLOCKED_UPLOAD_TYPES`

The declared types a browser runs when it opens the file (HTML, SVG, JavaScript, XML), named
outright. Every provider refuses to store them unless the route was created with
`receiveUploads({ allowActiveTypes: true })`. The declared type is the client's claim, so this is
the second layer: the first is serving every file with {@link sendUpload}.

This is not the whole rule: a browser also runs every other `+xml` type (`application/atom+xml`)
and every script type (`text/jscript`). To ask whether a type is one a browser runs, call
{@link isBlockedUploadType}; never test membership here.

```typescript
const BLOCKED_UPLOAD_TYPES: ReadonlySet<string>
```

#### `INLINE_UPLOAD_TYPES`

The types {@link sendUpload} shows in the browser when asked to: none of them can run code there.


### Runtime Dependencies

- `@molecule/api-bond`
- `@molecule/api-i18n`
- `@molecule/api-middleware-body-parser`

A weak upload integration leaks files or trusts the client. {@link receiveUploads} does the
request side: it refuses wrong types, oversized files, extra files and non-multipart bodies
before the handler runs, removes partial files when a request fails or the client disconnects,
and removes the stored files when the route then fails. The handler still owns the rest:

- **Own every file.** Persist the returned {@link UploadedFile} id with the uploader's
  `user_id`, and on read/delete load the row and 404 if it isn't the caller's — an
  unscoped `getFile(id)` is an IDOR (anyone enumerates everyone's files).
- **Put the auth check before `receiveUploads`**, so an anonymous request is refused before
  anything is stored.
- **Serve a stored file with {@link sendUpload}**, not `stream.pipe(res)`, which sends no type
  and lets the browser guess one: a file whose declared type lied would run on the app's
  origin. `sendUpload` sends `application/octet-stream` as an attachment with `nosniff`;
  `{ inline: true, type: file.mimetype }` shows an image, audio, video or plain text file.
- **The declared type is the client's claim.** `types` refuses what the client declares, and
  every provider refuses the types a browser runs (HTML, SVG, JavaScript, every XML type) with 415. A route that stores any file, served back only through `sendUpload`, passes
  `allowActiveTypes: true`; a route that shows its files to users (an avatar) never does. When
  the content matters (an image you render), check the stored bytes too.
- **A failed route keeps nothing.** When the handler throws, or answers with a status of 400 or
  more, `receiveUploads` removes the files it stored. A client that goes away before the answer
  removes nothing: the handler may already have saved what points at the file. Call
  `discardUploads(req)` only when the handler fails yet answers 2xx (the failure in the body), so
  the stored files do not stay with nothing pointing at them.
- **Use `receiveUploads` rather than a multipart parser of your own.** The bundled provider
  bonds cap a file's size only through the parser's `'limit'` event on the stream
  (`'Stream limit reached.'` on `onError`); a plain stream is never size-limited.
- **Private by default.** Do NOT put user uploads on a public, guessable path; serve them
  through an authenticated route (or a short-lived signed URL). Public buckets leak files.
- **Persist the id, never the provider URL.** Store `file.id` (or a serve URL you build from
  it, e.g. `/api/files/<id>`) — NEVER the raw `file.location`. A bucket URL 403s the moment
  storage is private (the default here), so a rendered `location` works only on the local
  filesystem bond and breaks on S3; and only the id lets a later route serve, delete, or
  REPLACE the object. Persisting `location` strands the file — uncleanable.
- **Free the blob on delete AND replace.** Deleting the owning row must also call
  `deleteFile(id)` — a row-only delete orphans the object in storage forever. On REPLACE (a
  new upload overwriting a stored id) `deleteFile` the OLD id too, or every change leaks the
  previous blob. Both are best-effort (log, don't fail the request) and run AFTER the row
  write so a storage hiccup never leaves a row pointing at a gone object.
- **Never build a storage key from the raw client filename** — sanitize/generate the key
  server-side (path traversal / overwrite).
- Stream to storage (the API takes a `NodeJS.ReadableStream`); never buffer a whole upload
  in memory.
- **Aborting an upload is neither a success nor a failure.** `abortUpload()` rejects the
  file's `uploadPromise` with {@link UploadAbortedError} — it never resolves `uploadPromise`
  and never invokes the `upload()` call's `onError` for the abort itself — and what was written
  of the file is removed. This holds across
  every bundled provider, so swapping providers never changes what a consumer observes on
  abort. See {@link UploadAbortedError} for the full contract.

## E2E Tests

Integration checklist — drive the real UI (live preview, no mocks), adapt
each item to this app's actual screens/flows, and check every box off one
by one. A box you can't check is an integration bug to fix — not a skip:

- [ ] Uploading a valid file through the UI shows progress/confirmation and the
      file appears in the user's file list.
- [ ] The uploaded content is retrievable: opening/downloading it returns the
      same content (an uploaded image actually renders).
- [ ] A disallowed file type is rejected with a visible error and does NOT
      appear in the list.
- [ ] An over-the-cap file is rejected cleanly (visible error, no partial
      phantom entry).
- [ ] Ownership is enforced: a second signed-in user cannot retrieve the first
      user's file by its id/URL (404 — not the file).
- [ ] Deleting a file removes it from the list, and it stays gone (and
      unretrievable) after a full reload.
