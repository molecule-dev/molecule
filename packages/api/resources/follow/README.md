# @molecule/api-resource-follow

Follow/unfollow resource for molecule.dev.

Polymorphic follow system for users or any resource type. Supports
followers list, following list, and follow status checks.
Use `getFollowedIds(viewerId, targetType, ids)` once per displayed collection, then
`followed.has(id)` for each item. It uses one query with no pagination truncation,
deduplicates ids, and does no I/O for an empty page or an absent viewer. It works for
any target type, including documents, topics and users. Use `isFollowing` for one target.

**Custom routes use the same services.** A profile route, username parameter or
different response envelope does not require the package's HTTP routes. Resolve
the username in the app, then call `follow(viewerId, 'user', profile.id)`,
`unfollow(viewerId, 'user', profile.id)` or
`isFollowing(viewerId, 'user', profile.id)` and project the profile locally.
`isFollowing` accepts `string | null | undefined`; an absent viewer returns
`false` without a database read. Mutations still require an authenticated id.

These services use the package's `follows` table, with `followerId`, `targetType`
and `targetId`. For users, `targetId` is the canonical user id, never the username.
A genuinely different relationship schema stays local; these calls do not read a
custom `followingId` column or a separate table.

```typescript
import { getFollowedIds } from '@molecule/api-resource-follow'

export async function projectWatchedNotes(
  notes: readonly { id: string; title: string }[],
  viewerId?: string | null,
) {
  const followed = await getFollowedIds(
    viewerId,
    'note',
    notes.map(({ id }) => id),
  )
  return notes.map((note) => ({ ...note, watching: followed.has(note.id) }))
}
```

#### `follow(followerId, targetType, targetId)`

Creates a follow relationship. Idempotent — returns existing follow if already following.

`targetId` is stored exactly as supplied: the package does not resolve a
username or display handle to an id, and does not require the target to
exist. For `targetType` `'user'`, pass the target's user `id` — the same
identity the rest of the app keys that user's rows by (an app using
`@molecule/api-resource-article`'s feed stores that id in `articles.authorId`,
which the feed matches against `targetId`); a route that receives a username
resolves it first. For any other `targetType`, the canonical id is whatever
the app's own reader of that resource uses. Pass the SAME value to
`unfollow` and `isFollowing`, or those calls target a different follow.

#### `getFollowedIds(followerId, targetType, targetIds)`

- **List endpoints return a PAGINATED envelope** `{ data, total, limit, offset }`, not a
  bare array — read the rows off `result.data` (server). On the client, `unwrapList(res)`
  from `@molecule/app-http` normalizes this envelope (pass it the whole HttpResponse), so
  the rows come back; reading the response as a bare array — or `res.data` alone (which is
  the envelope) — yields an EMPTY list.
  A scaffold that lists this package already has this table: its `__setup__` SQL is copied
  into the app at create time and replayed on every boot, so do not copy it into
  `api/migrations/` yourself — only a package added after the scaffold needs that.
  `src/__setup__/follows.sql` creates the single `follows` table. An
  mlcl-scaffolded API replays `__setup__/*.sql` on migrate (a `CREATE TABLE IF NOT EXISTS`, so a table the app's own migrations already create keeps only its own columns: ALTER in the ones it lacks);
  anywhere else run it once — nothing at runtime creates it.

The follower is ALWAYS the authenticated user: handlers read
`res.locals.session` (populated by your global auth middleware) and 401
without it — never accept a follower userId from the body or params.
`GET /:targetType/:targetId/followers` is deliberately PUBLIC; gate it
yourself if follower lists are private in your app.

`targetType` is a free-form string (`user`, `post`, …) — the package does
not validate it against your schema, so constrain accepted values in your
app if arbitrary types would be a problem.

## E2E Tests

Integration checklist — drive the real UI (live preview, no mocks), adapt
each item to this app's actual screens/flows, and check every box off one
by one. A box you can't check is an integration bug to fix — not a skip:

- [ ] User A follows user B (`POST /follow/user/:B`): B's follower count and
      A's following count each increment by exactly one, B appears in A's
      following list (`GET /following`) and A appears in B's followers list
      (`GET /user/:B/followers`). Reload — the edge and both counts persist (it's
      a real `follows` row, not local UI state).
- [ ] Following is IDEMPOTENT: A following B a second time (double-tap Follow
      or replay the POST) creates NO duplicate edge and does NOT double-count —
      exactly one `follows` row exists for (A → B) and both counts are unchanged.
- [ ] Unfollow (`DELETE /follow/user/:B`) removes the edge: A's following
      count and B's follower count each decrement back, B leaves A's following
      list, A leaves B's followers, and `GET /follow/check/user/:B` now returns
      `{ following: false }`.
- [ ] You cannot follow yourself: the UI never offers Follow on your own
      profile, and following your own id never inflates your own counts. This
      package's `follow()` does not reject `followerId === targetId`, so the app
      must guard it — verify the guard exists, don't assume it.
- [ ] AUTHORIZATION — the follower is ALWAYS the session user: handlers read
      `res.locals.session` and 401 without it, so no UI or endpoint lets you
      follow/unfollow on behalf of another user by passing their id, and
      follow/unfollow act only on your own edges. Signed in as A you can never
      make B follow or unfollow anyone.
