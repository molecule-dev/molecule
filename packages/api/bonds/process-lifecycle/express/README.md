# @molecule/api-process-lifecycle-express

Express/Node provider for `@molecule/api-process-lifecycle`.

Gives a scaffolded API the operational surface a rolling or blue/green
deploy needs out of the box:

- `GET /health/live` — is the process alive (200 while draining too).
- `GET /health/ready` — may a load balancer route here (503 while draining,
  or when a critical readiness check fails).
- Request tracking with `Connection: close` on responses while draining.
- SIGTERM/SIGINT handlers that drain in-flight requests (default bound 25 s,
  `SHUTDOWN_TIMEOUT_MS`; load-balancer flip wait `SHUTDOWN_LB_FLIP_WAIT_MS`),
  run ordered shutdown hooks (database pool, Redis, queues), and exit 0.

## Quick Start

```typescript
import { installExpressLifecycle } from '@molecule/api-process-lifecycle-express'
import { registerReadinessCheck, registerShutdownHook } from '@molecule/api-process-lifecycle'

const app = express()
const lifecycle = installExpressLifecycle({ app }) // mounts /health/live + /health/ready

registerReadinessCheck({ name: 'database', check: async () => db.ping() })
registerShutdownHook({ name: 'database-pool', run: () => db.pool.end() })

const server = app.listen(4000, () => lifecycle.markReady())
lifecycle.attachServer(server)
```

#### `ProcessLifecycleProvider`

The contract every process-lifecycle provider implements.

Application code reaches the bonded provider through the accessors in

```typescript
interface ProcessLifecycleProvider {
  /** The current lifecycle phase. */
  state(): ProcessLifecycleState
  /** Move from `starting` to `ready` once the boot sequence has finished. */
  markReady(): void
  /** `true` while draining or stopped. */
  isDraining(): boolean
  /** Begin draining: readiness reports not-ready from this call onward. Idempotent. */
  startDraining(reason?: string): void

   * request; it is idempotent so a `finish`/`close` pair cannot double-count.
   */
  beginRequest(): () => void
  /** Number of requests currently being served. */
  inFlightRequests(): number
  /**
   * Resolve `true` when the in-flight count reaches zero, or `false` when
   * `timeoutMs` elapses first.
   */
  waitForRequestsToDrain(timeoutMs: number): Promise<boolean>
  /**
   * Register a named readiness check.
   *
   * @returns A function that removes the check.
   */
  registerReadinessCheck(check: LifecycleCheck): () => void
  /**
   * Register a named liveness check.
   *
   * @returns A function that removes the check.
   */
  registerLivenessCheck(check: LifecycleCheck): () => void
  /**
   * Register an ordered shutdown hook.
   *
   * @returns A function that removes the hook.
   */
  registerShutdownHook(hook: ShutdownHook): () => void
  /**
   * Register a named boot warm-up step.
   *
   * Steps registered before {@link ProcessLifecycleProvider.markReady} run as
   * one pass when it is called; readiness stays closed until every step has
   * completed or timed out.
   *
   * @returns A function that removes the step.
   */
  registerWarmupStep(step: WarmupStep): () => void
  /**
   * Run every registered warm-up step once.
   *
   * Idempotent: a second call joins the in-flight pass instead of running the
   * work again. Never rejects — a failing or hanging step is reported.
   *
   * @returns The per-step warm-up report.
   */
  runWarmup(): Promise<WarmupReport>
  /**
   * Whether the boot warm-up has settled (every step completed or timed out).
   *
   * @returns `true` once the warm-up pass has finished.
   */
  isWarm(): boolean

   * load-balancer flip window.

   * @returns A function that removes the hook.

  registerDrainHook(hook: DrainHook): () => void

  isReady(): Promise<ReadinessReport>
  /** Run every liveness check and report whether the process is alive. */
  isLive(): Promise<LivenessReport>
  /** Run every shutdown hook in order, then mark the process stopped. Idempotent. */
  runShutdownHooks(reason?: string): Promise<ShutdownReport>
```

#### `mountLifecycleRoutes(app, provider)`

Mount `GET /health/live` and `GET /health/ready` on an Express app.

- `/health/live` answers 200 while the process is alive, including while
  draining — a liveness probe must not restart a process that is finishing
  its in-flight work.
- `/health/ready` answers 200 only when the process is ready, the boot
  warm-up has settled, consecutive probes have passed, and every critical
  check passes; 503 while draining (with `Connection: close`), while the
  warm-up runs, or when a critical check fails. The body's `warm` field says
  whether the warm-up is what is holding the instance back.

Both responses are `Cache-Control: no-store`.

- `provider` — The lifecycle provider that computes the reports.

#### `installGracefulShutdown(options)`

Install SIGTERM/SIGINT handlers that drain and shut the process down cleanly.

The sequence, in order:

1. `provider.startDraining(signal)` — `/health/ready` answers 503 from this
   instant, so a load balancer stops routing here.
2. Run the registered drain hooks (bounded, never fatal). A hook that throws
   does not skip step 3.
3. Wait `flipWaitMs` while the listener is still open, giving the load
   balancer time to observe the 503 before the connection is refused. The
   window is derived from `LB_HEALTHCHECK_INTERVAL_MS` /
   `LB_HEALTHCHECK_TIMEOUT_MS` when those are declared, and a window too
   short for them logs one warning at boot.
4. `closeIdleConnections()` then `server.close()` — no new connections are
   accepted, and a proxy holding an idle keep-alive socket must open a new
   one; responses already in flight carry `Connection: close`.
5. Wait up to `drainTimeoutMs` for the in-flight count to reach zero. If the
   bound expires (an SSE/WebSocket stream, a stuck handler), log it and
   `closeAllConnections()`.
6. Run the ordered shutdown hooks (database pool, Redis, queues, …).
7. Exit `0`.

A second signal while the first is still draining exits `1` immediately
rather than stacking a second drain. The handlers never throw.

```typescript
function installGracefulShutdown(options: GracefulShutdownOptions): GracefulShutdownHandle
```

- `options` — The server, provider, bounds, logger and exit function.

**Returns:** A handle exposing the same sequence (`stop`) and `uninstall`.
