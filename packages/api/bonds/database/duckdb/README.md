# @molecule/api-database-duckdb

DuckDB database provider for molecule.dev — an embedded analytical SQL
engine that queries Parquet, CSV and JSON files in-process.

Provides DatabasePool and DataStore implementations backed by
`@duckdb/node-api` (DuckDB 2.0). DuckDB is the SQLite shape, but
columnar/OLAP: it is the right bond for analytics over files
(`SELECT * FROM read_parquet('events.parquet')`), aggregations and ad-hoc
slices — not for a high-write-rate OLTP app (that is the postgresql bond's
job).

DuckDB cannot reproduce a foreign key's `ON DELETE`/`ON UPDATE` `CASCADE`,
`SET NULL` or `SET DEFAULT` action, and this bond refuses to silently drop
it: a resource whose setup SQL needs one is refused by the generator's
compatibility preflight ({@link sqlCapabilities}) before an app is built.

#### `ConnectionLock`

Serializes every use of ONE DuckDB connection.

All connections from one instance share one database, and DuckDB detects
conflicting writes across connections of one instance as transaction
conflicts — an interactive `BEGIN` … `COMMIT` interleaved with writes from
another connection fails the transaction. So this pool uses ONE connection
(the sqlite bond's model): plain `query()` calls hold it for one statement;
`connect()` and `transaction()` hold it until they are released, so a
transaction's `BEGIN` → … → `COMMIT`/`ROLLBACK` runs alone.

Waiting is bounded: a waiter that cannot get the lock within its timeout is
removed from the queue and rejected with an error naming the likely cause
(code holding a connection while calling the pool), instead of hanging forever.

```typescript
class ConnectionLock {
  private locked = false
  private holder: string | null = null
  private waiters: Array<{ grant: () => void }> = []

  /**
   * Number of callers currently waiting for the lock.
   *
   * @returns The queue length.
   */
  get waiting(): number {
    return this.waiters.length
  }

  /**
   * Whether the lock is currently held.
   *
   * @returns `true` when held.
   */
  get isLocked(): boolean {
    return this.locked
  }

  /**
   * Waits for the lock in FIFO order. The returned release function MUST be
   * called exactly once; extra calls are ignored.
   *
   * @param purpose - What the caller will do with the lock (`'query'`,
   *   `'connect()'`, `'transaction()'`), used in the timeout message.
   * @param timeoutMillis - Maximum wait; `0` or less waits forever.
   * @returns A release function.
   */
  acquire(purpose: string, timeoutMillis: number): Promise<() => void> {
    let released = false
    const release = (): void => {
      if (released) return
      released = true
      this.holder = null
      const next = this.waiters.shift()
      if (next) {
        next.grant()
      } else {
        this.locked = false
      }
    }

    if (!this.locked) {
      this.locked = true
      this.holder = purpose
      return Promise.resolve(release)
    }

    return new Promise<() => void>((resolve, reject) => {
      let timer: ReturnType<typeof setTimeout> | undefined
      const waiter = {
        grant: (): void => {
          if (timer !== undefined) clearTimeout(timer)
          this.locked = true
          this.holder = purpose
          resolve(release)
        },
      }
      this.waiters.push(waiter)
      if (timeoutMillis > 0) {
        timer = setTimeout(() => {
          const index = this.waiters.indexOf(waiter)
          if (index === -1) return
          this.waiters.splice(index, 1)
          reject(
            new Error(
              `DuckDB: a ${purpose} waited ${timeoutMillis} ms for the pool's single ` +
                `connection, which is held by an open ${this.holder ?? 'operation'}. This pool ` +
                `serializes everything on one connection: release() a connect()ed connection and ` +
                `commit()/rollback() a transaction before calling the pool or the store again, and ` +
                `run every statement of a transaction on its own query().`,
            ),
          )
        }, timeoutMillis)
      }
    })
  }
}
```

#### `acquireInstance(config)`

Open (or join) the instance for a pool.

A FILE path goes through `DuckDBInstance.fromCache`: the official answer to
"two instances must never open the same file" — every pool in this process
on one file shares one instance (and one write lock). In-memory databases
are always PRIVATE (a shared `:memory:` cache entry would hand two test
pools one database), so they use a fresh `create` and are closed when their
last pool ends. File-backed cached instances are NEVER closed by this
module: the client's cache has no eviction, and closing a cached instance
would hand the next `fromCache` caller a dead one — they live for the
process, which is also why a file path must not be reused across processes

#### `translateDdlToDuckdb(sql, options)`

Translate PostgreSQL-dialect DDL to DuckDB-compatible DDL at migration time.

Resource/template setup migrations are authored in PostgreSQL dialect. DuckDB
2.0 already speaks most of it natively — `uuid`/`timestamptz`/`bytea`/`text[]`
type names, `gen_random_uuid()`, `now()`, `CURRENT_TIMESTAMP`, `::` casts,
`ADD COLUMN IF NOT EXISTS`, `DROP COLUMN IF EXISTS`, `ON CONFLICT`, `ILIKE` —
all verified against 2.0.0-r.1. The constructs it rejects are rewritten here,
and only where the rewrite preserves behaviour:

- `jsonb` → `json`, in both the column-type position and the `::jsonb` cast
  (DuckDB has a `JSON` type, stored as VARCHAR; there is no `jsonb`).
- `USING <method>` on a `CREATE INDEX` (`gin`/`btree`/`hash`/`gist`) →
  removed: DuckDB indexes have no access method.
- A partial index gets no `WHERE` support in DuckDB. A non-unique partial
  index becomes a full index on the same columns — the predicate only narrows
  which rows the index covers, never a query's result. A UNIQUE partial index
  becomes a UNIQUE index over `CASE WHEN <predicate> THEN <column> END` per
  column: rows outside the predicate get NULL keys (distinct in DuckDB), so
  uniqueness applies to exactly the rows PostgreSQL would constrain.

What it does NOT rewrite is an `ON DELETE`/`ON UPDATE` referential action
(`CASCADE`, `SET NULL`, `SET DEFAULT`): DuckDB rejects the clause at parse
time and has no triggers, so dropping it would turn a cascading delete into a

_(description truncated — read the full text in `node_modules/@molecule/api-database-duckdb/dist/utilities.d.ts`.)_

```typescript
function translateDdlToDuckdb(sql: string, options?: TranslateDdlOptions): string
```

- `sql` — Raw migration SQL, possibly in Postgres dialect.
- `options` — The source file name used in an unsupported-construct error.

**Returns:** DuckDB-compatible SQL.

### Runtime Dependencies

- `@duckdb/node-api`
- `@molecule/api-bond`
- `@molecule/api-database`
- `@molecule/api-secrets`

Configure via the `DUCKDB_PATH` environment variable (default:
`./data/app.duckdb`; `:memory:` for a database that lives only for the
process's lifetime).

- **`pool.query(text, values)` takes Postgres-style `$1, $2` placeholders —
  or `?` — natively, with no translation.** With VALUES a string must be
  ONE statement (the client prepares it); without values a multi-statement
  string runs in full and the LAST statement's result is returned.
  `rowCount` follows node-postgres: rows returned for a SELECT or
  `…RETURNING` statement, rows changed for plain INSERT/UPDATE/DELETE,
  `null` for DDL.
- **One process per file, in read-write mode.** DuckDB holds a file lock:
  the dev server and a CLI must never open the same `.duckdb` file
  read-write at the same time (`Could not set lock on file`). This pool
  shares one instance per file inside the process (`fromCache`) and
  serializes every statement on ONE connection behind a FIFO queue, the
  sqlite bond's model — a `transaction()` holds the queue for its whole
  `BEGIN` → … → `COMMIT`/`ROLLBACK` lifetime. A second PROCESS wanting
  concurrent reads should open `readOnly: true`.
- **Resource defaults differ from DuckDB's own.** DuckDB defaults to 80% of
  RAM for `memory_limit` and one thread per core — enough to eat a shared
  host. This bond defaults to `memory_limit: '1GB'` and `threads: 4`,
  overridable via `DUCKDB_MEMORY_LIMIT` / `DUCKDB_THREADS` or the
  `memoryLimit`/`threads` config fields.
- **Files are the point:** `read_parquet`, `read_csv`, `read_json` and the
  `'file.parquet'` shorthand all work through `pool.query()` as plain SQL.
  They read relative to the API process's working directory.
- **JSON columns read as JSON TEXT through raw `query()`** — DuckDB's
  `JSON` type is an alias over VARCHAR, so the type is invisible in result
  metadata. The DataStore CRUD helpers (`create`, `findMany`, …) parse
  JSON-typed columns for you; in raw SQL use `data -> 'key'` /
  `json_extract` or accept the string.
- **`COUNT(*)` and BIGINT come back as JS numbers** when they fit
  `Number.MAX_SAFE_INTEGER` (raw DuckDB returns `bigint`, which
  `JSON.stringify` throws on); a larger value becomes its decimal string,
  matching node-postgres.
- **Schema changes are `*.sql` files in the app's `api/migrations/`**,
  applied in lexical order on startup by `createMigrator`. Postgres-dialect
  DDL applies after a translation that keeps behaviour: `jsonb` → `json`,
  index `USING <method>` dropped, and a partial index applied as a full index
  or (UNIQUE) as a `CASE WHEN` expression index. `gen_random_uuid()`,
  `now()`, `ADD/DROP COLUMN IF [NOT] EXISTS`, `::` casts and `uuid`/
  `timestamptz`/`bytea`/`text[]` types are native. An `ON DELETE`/
  `ON UPDATE` referential action throws `UnsupportedSqlFeatureError` —
  DuckDB cannot reproduce it; each file runs once (recorded in
  `_molecule_migrations`) and in one transaction.
- **2.0 file format is a one-way break:** versions before DuckDB 2.0 cannot
  read files this bond creates (2.0 still reads 1.x files). The engine is
  OLAP — bulk scans and aggregations are its home; an app doing many small
  row transactions belongs on the postgresql bond.
- `pool.end()` closes the pool's connection; a FILE-backed instance is
  process-lifetime by design (the client's instance cache has no eviction).
